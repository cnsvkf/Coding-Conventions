# 2. Kotlin·Android: 역할이 드러나는 이름 짓기

## 이번 문서에서 배울 내용

변수·함수·클래스 이름만 읽어도 그 대상이 맡은 역할을 짐작할 수 있도록 이름을 짓습니다. 이름이 분명하면 코드를 처음 읽는 사람도 주변 코드를 계속 찾아보지 않고 내용을 따라가기 쉽습니다.

## 모호한 이름은 왜 불편할까요?

`data`, `value`, `item`, `result`, `temp`, `obj`, `manager`처럼 넓은 뜻을 가진 이름은 코드가 짧아도 무엇을 가리키는지 알려 주지 못할 수 있습니다. 특히 비슷한 값이 여러 개 있는 함수에서는 이름만 보고 역할을 구별하기 어렵습니다.

## 이름에 역할 담기

| 모호한 이름 | 역할이 드러나는 이름 | 이름만 보고 알 수 있는 점 |
|---|---|---|
| `item` | `selectedBook` | 목록 중 선택된 책 |
| `result` | `loginResult` | 로그인 작업의 결과 |
| `temp` | `pendingRefreshToken` | 아직 적용되지 않은 갱신 토큰 |
| `manager` | `sessionTokenRefresher` | 세션 토큰을 갱신하는 역할 |

예를 들어 책 목록에서 선택한 항목을 사용한다면 다음처럼 쓸 수 있습니다.

```kotlin
val item = books[selectedIndex]
```

```kotlin
val selectedBook = books[selectedIndex]
```

두 번째 이름은 값의 형태뿐 아니라 이 코드에서 맡는 역할을 알려 줍니다. 함수와 클래스도 같은 기준으로 살펴봅니다. 이름이 `update`, `Manager`처럼 넓은 뜻에 머물러 있다면 무엇을 갱신하거나 관리하는지 드러나도록 구체화할 수 있는지 확인합니다.

## 이름을 정할 때 살펴볼 점

- 이름이 가리키는 값이나 동작의 역할이 보이는가?
- 같은 범위에 비슷한 이름이 있어 서로 헷갈리지 않는가?
- 더 구체적인 이름을 썼을 때 코드 읽기가 쉬워지는가?
- 프로젝트의 기존 파일·패키지·이름 규칙과 맞는가?

`data`나 `result`가 항상 잘못된 것은 아닙니다. 가까운 문맥만으로 뜻이 충분히 분명하다면 간결한 이름도 괜찮습니다. 판단 기준은 이름 하나만 봤을 때뿐 아니라 주변 코드와 함께 읽었을 때 역할을 구별할 수 있는지입니다.

## 핵심 정리

- 변수·함수·클래스 이름에 역할과 의미를 담습니다.
- 넓은 이름은 문맥에서 뜻이 분명하지 않을 때 더 구체적으로 바꿉니다.
- 한 범위 안에서 서로 다른 대상을 혼동하지 않도록 이름을 구별합니다.
- 대소문자와 파일 배치 같은 세부 규칙은 해당 프로젝트의 관례를 따릅니다.
