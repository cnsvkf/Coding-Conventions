# 3. Kotlin·Android: 주석과 라이브러리 추가

## 이번 문서에서 배울 내용

- 주석은 **무엇을 할지가 아니라 왜 그렇게 했는지**를 적는다는 원칙
- 새 라이브러리를 넣기 전에 확인할 것
- 빌드 의존성을 버전 카탈로그로 관리하는 이유

## 1. 주석은 이유를 적는다

코드가 이미 말하고 있는 내용을 한국어로 옮겨 적으면 금방 낡고 읽는 시간만 늘립니다.

나쁜 예:

```kotlin
// 토큰을 저장한다
fun saveToken(token: String) { ... }
```

좋은 예:

```kotlin
// 서버가 refresh token을 회전시키므로, 응답 값으로 항상 덮어쓴다.
fun saveToken(token: String) { ... }
```

두 번째 주석은 "왜 이 방식을 택했는지"를 알려 줍니다. 다음 사람이 "이전 토큰을 남겨 두면 안 되나?"를 고민하지 않게 합니다.

### 역할 주석은 공개 진입점에만

외부에서 부르는 핵심 함수(유스케이스의 실행 함수, 뷰모델의 사용자 이벤트 처리 등)는 이름만으로 업무 의미가 다 드러나지 않을 때 **한 줄 역할 주석**을 달 수 있습니다. getter나 단순 위임 함수에는 달지 않습니다.

## 2. 라이브러리를 넣기 전 질문

새 의존성은 한 번 들어가면 계속 관리해야 합니다. 추가하기 전에 다음을 확인합니다.

- 기존 의존성으로 같은 기능을 할 수 있는가?
- 유지보수가 이어지고 있는가?
- 프로젝트의 Kotlin, Android 버전과 호환되는가?
- 라이선스와 보안 이력에 문제가 없는가?
- 앱 크기와 성능에 얼마나 영향을 주는가?

중요한 라이브러리라면 이유를 적고 팀에 확인받습니다.

## 3. 버전은 한 곳에서 관리한다

`gradle/libs.versions.toml` 같은 버전 카탈로그가 있다면, 버전 문자열을 build 스크립트에 직접 쓰지 않습니다. 버전 변경이 한 파일에서 끝나고, 모듈마다 다른 버전이 섞이는 실수가 줄어듭니다.

Compose 라이브러리는 BOM을 쓰는 프로젝트라면 BOM으로 버전을 맞추는 것이 기본입니다. 개별 버전을 따로 고정하면 BOM과 충돌할 수 있습니다.

## 핵심 정리

- 주석은 "무엇"보다 "왜"를 씁니다.
- 공개 핵심 진입점에만 한 줄 역할 주석을 허용합니다.
- 라이브러리는 기존 방식으로 안 될 때만, 검토 항목을 거쳐 추가합니다.
- 버전은 카탈로그와 BOM으로 한 곳에서 관리합니다.
