# 3. 변경 후 스스로 검토하기

## 이번 문서에서 배울 내용

코드를 고친 직후 무엇을 다시 확인해야 하는지, 그리고 완료 보고에 무엇을 적어야 하는지 익힙니다.

## 왜 "돌아가니까 끝"이면 안 될까요?

화면이 한 번 열린다고 해서 작업이 끝난 것은 아닙니다. 요구사항을 빠뜨렸을 수도 있고, 기존 기능이 조용히 사라졌을 수도 있습니다. 스스로 다시 읽는 몇 분이 나중의 긴 버그 추적을 줄입니다.

## 자가 검토 질문

1. **요구사항:** 사용자가 요청한 것을 정확히 만들었는가?
2. **기존 기능:** 관련 없는 기능을 실수로 지우거나 바꾸지 않았는가?
3. **구조:** 의존 방향이 자연스럽고, 같은 로직이 여러 곳에 복사되지 않았는가?
4. **이름:** 변수와 함수 이름이 역할을 드러내고, 서로 헷갈리지 않는가?
5. **오류 처리:** 실패할 때의 경로가 빠지지 않았는가? null 가능성은 처리했는가?
6. **가져오기와 참조:** 옮기거나 지운 파일을 가리키는 코드가 남아 있지 않은가?

## 구조를 옮겼을 때 추가로 볼 것

파일이나 폴더를 옮기면 가져오기 경로와 참조가 깨지기 쉽습니다. 옮긴 뒤에는 빌드나 타입 검사를 한 번 돌려 깨진 곳이 없는지 봅니다.

## 검증 결과는 사실대로

- 실제로 실행한 빌드와 테스트는 결과와 함께 적습니다.
- 실행하지 못한 검증은 성공 목록에 넣지 말고, 이유(환경, 시간, 권한)와 함께 따로 적습니다.
- 확인하지 않은 내용을 확인했다고 쓰지 않습니다.

## 완료 보고에 담을 것

- 무엇을 바꿨는지와 어떤 파일을 건드렸는지
- 기존 코드에 미칠 수 있는 영향
- 실행한 검증과 결과
- 남아 있는 문제나 확인이 필요한 사항

## 핵심 정리

- 변경 후에는 요구사항, 기존 기능, 구조, 이름, 오류 처리를 스스로 다시 봅니다.
- 구조를 바꿨다면 참조가 깨지지 않았는지 따로 확인합니다.
- 완료 보고는 실제로 한 검증과 못 한 검증을 구분해서 씁니다.

## 복습 질문

1. 빌드가 성공했다면 자가 검토를 생략해도 되나요? 이유는 무엇인가요?
2. 파일을 옮긴 뒤 특히 확인해야 할 것은 무엇인가요?
3. 실행하지 못한 테스트를 완료 보고에 어떻게 적어야 하나요?
