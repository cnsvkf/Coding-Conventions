# 1. 새 기능을 만들기 전에 프로젝트 규칙부터 살펴보기

## 이번 문서에서 배울 내용

기존 코드베이스에 기능을 추가할 때는 새로운 방식을 먼저 고르기보다, 그 프로젝트가 이미 정한 규칙과 사용 중인 구조를 살펴봅니다. 그래야 새 코드가 기존 코드와 자연스럽게 연결되고, 팀원도 같은 방식으로 이해하고 고칠 수 있습니다.

## 프로젝트마다 방식이 다른 이유

같은 기능도 프로젝트마다 구현 방식이 다를 수 있습니다. 화면을 만드는 도구, 화면 상태를 관리하는 방법, 화면 이동 방식, 의존성을 연결하는 방법 등이 이미 정해져 있을 수 있습니다.

새 기능만 다른 도구나 구조로 만들면 비슷한 일을 두 가지 방식으로 관리하게 됩니다. 기능을 고칠 때 어디에 무엇을 수정해야 하는지 찾기 어려워지고, 함께 작업하는 사람도 새 규칙을 따로 배워야 합니다.

## 먼저 살펴볼 것

1. **프로젝트 안내 문서**: 저장소의 `AGENTS.md`와 프로젝트 안의 스킬 문서가 있으면 먼저 읽습니다. 이 문서들은 해당 프로젝트에서 지켜야 할 규칙을 알려 줍니다.
2. **비슷한 기존 기능**: 새로 만들 기능과 가장 가까운 화면이나 모듈을 찾아 어떤 도구와 구조를 쓰는지 살펴봅니다.
3. **반복되는 패턴**: 여러 기능에서 공통으로 쓰는 이름, 파일 위치, 상태 관리, 화면 이동 방식을 확인합니다.

프로젝트별 안내와 기존 코드에서 확인한 방식은 일반적인 학습 자료나 개인 취향보다 우선합니다. 전역 규칙은 프로젝트에서 정하지 않은 부분을 채우는 기준으로 활용합니다.

## 예시: 기존 화면에 검색 기능 추가하기

어떤 앱이 화면을 Jetpack Compose로 만들고, 기존 화면 상태와 이동을 일정한 방식으로 관리한다고 해 봅시다.

새 검색 화면을 추가할 때는 먼저 비슷한 기존 화면을 살펴봅니다. 그 화면이 사용하는 UI 구성 방식과 상태 연결, 이동 경로를 따라가면 새 화면도 앱의 나머지 부분과 같은 방식으로 동작하게 만들 수 있습니다.

반대로 다른 튜토리얼에서 본 XML 화면이나 별도의 상태 관리 라이브러리를 바로 추가하면, 앱 안에 비슷한 역할을 하는 방식이 여러 개 생길 수 있습니다. 새 도구가 꼭 필요하다면 기존 방식으로 해결하기 어려운 이유부터 확인합니다.

> 이 예시는 한 가지 가능한 상황을 설명합니다. 실제 프로젝트에서 다른 도구나 구조를 사용한다면 그 프로젝트의 방식을 따릅니다.

## 시작 전 짧은 점검

- 저장소에 프로젝트 안내 문서가 있는가?
- 비슷한 기능은 어디에 있고, 어떤 방식으로 구현되어 있는가?
- 기존 방식으로 새 요구사항을 해결할 수 있는가?
- 새로운 구조나 도구를 추가해야 한다면 그 이유를 설명할 수 있는가?

## 핵심 정리

- 새 코드를 쓰기 전에 프로젝트의 안내와 주변 코드를 먼저 확인합니다.
- 이미 쓰고 있는 구조와 도구를 우선 이어서 사용합니다.
- 일반적인 규칙은 프로젝트 고유 규칙이 정하지 않은 부분에 적용합니다.
- 새 방식을 도입하기 전에는 기존 방식으로 해결할 수 없는 이유를 확인합니다.

## 복습 질문

1. 새 기능을 만들기 전에 안내 문서와 비슷한 기존 기능을 살펴보는 이유는 무엇인가요?
2. 프로젝트마다 화면 상태 관리 방식이 다를 때, 어떤 기준으로 새 기능의 방식을 정해야 하나요?
3. 기존과 다른 라이브러리나 구조를 추가하고 싶다면 무엇을 먼저 확인해야 하나요?
